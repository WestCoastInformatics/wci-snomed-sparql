SNOMEDCT ECL implementation using SPARQL
===========================================

This project is about creating a SPARQL-based implementation of SNOMEDCT ECL.
Resources provided include an edition of SNOMED, a draft of a document with
examples of SPARQL queries for differnt kinds of ECL expressions, links to the
snomed owl github repository, links to the ECL specification and test examples,
and other related information

# Resources

* Draft ECL as SPARLQL document: `ECL as SPARQL.docx` (this provides prior work with examples
   of certain ECL queries and how they resolve to sparql queries)
* SNOMED owl toolkit: `https://github.com/IHTSDO/snomed-owl-toolkit` (also ../snomed-owl-toolkit)
* SNOMED ecl parser: `https://github.com/IHTSDO/snomed-ecl-parser` (also ../snomed-ecl-parser)
* ECL Specification: `https://docs.snomed.org/snomed-ct-specifications/snomed-ct-expression-constraint-language`
  * Find sublinks under "Behaviour specification with examples" sections
  * Find sublink for "Syntax Specification"
* A recent SNOMED edition (in SnomedCT_InternationalRF2_PRODUCTION_20261001T120000Z/)
* example of a project using gradle instead of maven: `../wci-common-java`
* SNOMED browser link 
 `https://snomedbrowser.org/?perspective=full&conceptId1=404684003&edition=MAIN/2026-10-01&release=&languages=en`

# TODO

Following is a writeup of where we want to go.  Please ask questions along the way.

The end goal is to create a software system (using the same spring and java versions
as snomed-owl-toolkit.  However, in this case use a gradle approach instead as shown
in `wci-common-java`). The service should support the following modes

* launch with a parameter pointing to a SNOMED release folder (which finds files in either
the top level of that folder or a Snapshot folder within that folder - support both modes).
This should run the owl converter to create a SNOMED owl file that includes the "isMemberOf"
declarations described in the "draft ECL as SPARQL document". The code for owl conversion
is in snomed-owl-toolkit, but it does not add the extra member of declarations so these should 
be added in AFTER, following generation of the stock owl file based on the refsets in the RF2
data provided
* launch with a parameter pointing to an Owl file generated by the prior step.  This laods
the data into owl-api and then should offer a POST REST endpoint that takes an ECL expression
which in the background should get parsed and turned into an appropraite sparql query
which then runs against the loaded data and returns the SNOMED code and name (rdfs:label?).
This endpoing should also support paging (via limit/offset query params).
* launch with a parameter that is a SNOMEDCT release version (e.g. 20261001) and it will
run all the ECL expressions from the "Behaviour specification with examples" against the
SNOMED browser for that version and gather the results into a src/test/resources/data
folder to "save" these results so they can be used for unit tests.  This is how we will
update the unit tests to later versions of the data.

Ensure there is a set of unit tests that align with the examples in the "Behaviour specification with examples"
discussed in the resource section.  Keep working until all of the examples properly work. Ask questions
as needed to resolve.  The "correct answers" for the unit tests for a given ECL expression should
be gathered by running that ECL expression against the SNOMED browser link provided.  To avoid
making too many calls to that service, first make a series of calls for those examples and save
the results in a way that can be used to verify the unit tests.  The unit tests will require
a specific version of SNOMED to be loaded and we should settle on 20261001, so the Owl file
(with isMemberOf annotations) needs to be created and saved in src/test/data so it is available
going forward.
